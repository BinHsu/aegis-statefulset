# `infrastructure/terraform/bootstrap/` — state backend prerequisites

Stage-0 terraform module. Provisions the resources the main composition
depends on as its state backend:

| Resource | Purpose |
|---|---|
| S3 bucket (versioned, encrypted, public-blocked) | State storage for `infrastructure/terraform/` main composition |
| DynamoDB table (PAY_PER_REQUEST, PITR enabled) | State lock — prevents concurrent applies |

## Why a separate module

The state backend cannot live in the state file it manages — that would
be self-referential (chicken-and-egg). This module runs with a **local
backend**, persists its own small state file under
`infrastructure/terraform/bootstrap/terraform.tfstate` (gitignored), and
provisions the resources that the main composition then uses as its S3
backend.

## One-time setup

```bash
# 0. Have SSO + break-glass session if applicable (SCP-managed accounts):
source scripts/dev/runbook-00-bootstrap.sh
source scripts/dev/assume-break-glass.sh   # or assume-controltower.sh

# 1. Initialise + apply (local backend)
cd infrastructure/terraform/bootstrap
terraform init
terraform apply

# 2. Capture outputs
terraform output -raw backend_hcl_template > ../backend.hcl
terraform output
#   tfstate_bucket = "aegis-statefulset-tfstate-staging-251774439261"
#   tflock_table   = "aegis-statefulset-tflock-staging"
#   region         = "eu-central-1"

# 3. Initialise the main composition with the new backend
cd ..
terraform init -backend-config=backend.hcl
#   Terraform will offer to migrate any existing local state. If this is
#   the first time, there is no state to migrate — proceed.
```

## After bootstrap — wire into main composition

The main composition's `versions.tf` declares an empty `backend "s3" {}`
block; runtime values come from `backend.hcl` (gitignored, generated by
the bootstrap output above).

## Re-running

Re-running `terraform apply` is safe — both resources have
`prevent_destroy = true` lifecycle blocks. No-op if already provisioned.

## Teardown

The state backend deliberately resists teardown:
- S3 bucket has `prevent_destroy = true` — manually empty + edit terraform
  to remove the lifecycle block before `terraform destroy`
- DynamoDB table has `prevent_destroy = true` — same pattern

`scripts/teardown/full-teardown.sh` does NOT touch the bootstrap module
for this reason — the state backend outlives any specific demo run, and
losing it mid-teardown leaves orphaned resources without a state to
manage them from.
